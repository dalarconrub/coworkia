Cómo gestionar `toolkits/` en Coworkia: si debe ser parte versionada del repo, qué contenido admite y cómo evitar deuda por binarios portables.

## Alternativas

A. Versionar `toolkits/` completo: ZIPs + prompts.

## Criterios

| Criterio | Peso |
|---|---:|
| Portabilidad inmediata | 35 |
| Trazabilidad dentro del repo | 25 |
| Higiene Git / tamaño futuro | 25 |
| Mantenimiento simple | 15 |

## Matriz

| Alternativa | Puntuación | Ventajas | Riesgos |
|---|---:|---|---|
| A. Versionar completo | 86 | Todo queda reproducible y copiable sin depender de servicios externos; encaja con `memory/INDEX.md` y `memory/STRUCTURE.md` actuales. | Si los ZIPs crecen o se regeneran mucho, el historial Git se ensucia. |
| B. Solo prompts/manifiestos | 73 | Git queda limpio y los textos son revisables. | Pierde la promesa de kit portable listo para copiar. |
| C. Externalizar binarios | 62 | Escala mejor para artefactos pesados. | Añade fricción, enlaces rotos potenciales y dependencia externa para un sistema local. |

## Recomendación

Recomiendo A con regla de tamaño: mantener `toolkits/` versionado completo mientras los ZIPs sean artefactos portables pequeños y curados. Hoy el mayor (`multiagent-toolkit.zip`) pesa ~204 KB, así que el coste Git es bajo y la portabilidad compensa.

## Cuándo cambiaría esta recomendación

Cambiaría a B o C si los ZIPs pasan a ser generados frecuentemente, contienen dependencias pesadas, superan varios MB por artefacto, o empiezan a duplicar contenido reconstruible desde scripts.
